## v1.4.5 | 2026-11-21 | Pre-release | Fix warm-header startup stutter and throttled playhead slow-crawl
- **Scope**: `turbo-network`, `build-release`
- **Root Cause / Goal**: Real-server playback of 4K HEVC `敦煌英雄` (`15.1 Mbps`) exhibited a `1.5s-5.5s` stutter (`rebuf=1` at `1.536s`) right after an instant `14ms` warm open. Root causes: (1) `startDetailPreload` previously fetched Chunk 0 (`512 KiB`) alone before EOF, so interrupting preload left a warm-header / cold-body state (`Chunk 0 + EOF` only, ~`1.536s` of media) that ran dry before cold Chunk 1 returned on `1.8s-2.7s` TTFB edges; (2) `TurboStreamByteHandle.init` did not launch urgent `Chunk 1` when `Chunk 0` was already cached; (3) outer `4-6 MiB` H2 streams could starve a throttled playhead stream (`Chunk 1..3`) that dribbled bytes slowly without triggering idle-only rescue.
- **Changes**:
  - `Sources/DonbyNetwork/TurboCacheAndDownloadEngine.swift`:
    - `TurboStreamByteHandle.init`: Immediately launches `requestUrgentChunk(1)` when `Chunk 0` is warm and `Chunk 1` is missing.
    - `stepBulkPrefetchSchedule` & `handleChunkResponseHeaders`: Resets `chunkStartTimestamp` on response-header arrival and triggers a `1 MiB` rescue stream when an immediate playhead chunk (`idx <= currentChunk + 1`) crawls at `< 280 KB/s` for `> 1.8s`.
    - `spawnChunkFetchLocked`: Keeps outer lookahead spans compact at `2 MiB` (`4` chunks) while immediate playhead runway has `< 4` contiguous chunks (`< 2 MiB`).
    - `startDetailPreload`: Merges `Chunks 0..3` (`2 MiB`) into step 1's single Range RTT when starting at `0s`; `TieredAssetChunkStore.evictBehindCursor` retains `Chunks 0..3` alongside EOF Cues.
  - Bumped all 6 version locations to `1.4.5` and synced `docs/agent/modules/turbo-network.md` + `docs/agent/INDEX.md`.
- **Invariants & Pitfalls**: Keep cold TTFB rescue `>= 2.2s` (never conflate cold TTFB with post-header body crawl); never cap H2 concurrency to `2` streams.
- **Verification**: Real-server diagnostic on `敦煌英雄` (`DONBY_TEST_MUTED=1`, isolated `DONBY_HOME`): new preload step-1 scenario (`Chunks 0..3 + EOF`) opened in `10.1ms`, first frame in `71ms`, `rebuf=0`, `maxGap=67ms` (zero stutter); worst-case orphan `Chunk 0 + EOF` stutter halved from `5487ms` to `2826ms` with `8-11.75 MB/s` immediate recovery. L1 `swift build` passed; local Pre-release `v1.4.5` published.

## v1.4.2 | 2026-11-21 | Pre-release | Eliminate PGS/DVD subtitle find_stream_info probe stall
- **Scope**: `kernel-cpp`, `build-release`
- **Root Cause / Goal**: MKV files with embedded bitmap PGS subtitles (`hdmv_pgs_subtitle`) report `0x0` dimensions in container headers until the first spoken dialogue packet, causing FFmpeg `avformat_find_stream_info` to exhaust `probesize`/`analyzeduration` across extra network chunks (`98-802ms` wasted on startup).
- **Changes**:
  - `Sources/DonbyKernelC/dk_engine.cpp` (`dk_player_open_with_tracks`): Temporarily set `AVDISCARD_ALL` on subtitle streams and seed `1920x1080` on `0x0` `AV_CODEC_ID_HDMV_PGS_SUBTITLE` / `AV_CODEC_ID_DVD_SUBTITLE` streams before `avformat_find_stream_info`, then immediately restore original `discard` and `0x0` dimensions afterward; tightened non-TS `probesize` (`1 MiB`), `analyzeduration` (`500-600ms`), and `max_probe_packets` (`200`).
  - Bumped version to `1.4.2` across all 6 version locations (`build_app.sh`, `PlayerView.swift`, `AppUpdateManager.swift`, `EmbyClient.swift`, `UHDStreamClient.swift`, `docs/agent/INDEX.md`).
- **Invariants & Pitfalls**: Always restore subtitle `discard` and `0x0` dimensions right after `avformat_find_stream_info` so PGS/DVD decoders read true presentation dimensions from subtitle packets.
- **Verification**: Real-server A/B probe (`DONBY_TEST_MUTED=1`, isolated `DONBY_HOME`): Movie A `find_stream` dropped `801.8ms -> 14.9ms` (-98%, 0 PGS warnings, `pgssub` opened); Movie B `find_stream` dropped `98-142ms -> 33.8ms` (0 PGS warnings, `pgssub` opened); Release `/Applications/Donby.app` (`1.4.2`) built and signed.
